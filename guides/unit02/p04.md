In Project 03 you handed Ollama a prompt somebody else wrote. From here on the prompts are yours.

At the end of this project you will have a working game, and you will show it to Mr. Salemi.

# What you are building

Your teacher has assigned you one of five classic games: Pong, Breakout, Snake, Space Invaders, or Frogger.

You are building the plain version of it. It runs, you can play it, it keeps score, and it ends. Nothing fancy.

That plain working version has a name: the **MVP**, short for Minimum Viable Product. It is the smallest version of your game that is actually a game.

In Project 05 you turn it into your own version. Not yet.

# The PRD

A **PRD** is a Product Requirements Document. It describes what your program should do, in plain English, with no code in it.

Your PRD is the record of your game. Your chat with Ollama is not.

Chats get long and slow, and you will throw several away before this unit is over. The PRD stays. It grows a little every project.

It is also what you check your game against. If your PRD does not say it, you cannot check it.

# Exercise 1: Get Your Base Game Running

## Step 1: Make your game folder

```
cd $HOME
cd swdev
mkdir game
cd game
```

Projects 01 through 03 each got their own folder, because each one was a throwaway.

This folder is different. It holds your game for the rest of the term.

## Step 2: Start your PRD with one line

```
touch PRD.md
cot PRD.md
```

Find your game and type that one line into the CotEditor window. Read only your own game.

- Pong — `This is Pong.`
- Breakout — `This is Breakout.`
- Snake — `This is Snake.`
- Space Invaders — `This is Space Invaders.`
- Frogger — `This is Frogger.`

Save with **Command-S**.

That is the whole PRD for now. One line.

It is enough because Ollama already knows these games. It has read thousands of versions of them. You do not have to explain what a paddle is.

What it does not know is which version you want. That comes in Step 7, after you have seen what it gives you.

Leave the window open. You will be adding to this file for the rest of the term.

## Step 3: Ask Ollama for the game

Open the **Ollama** app.

At the bottom of the window is the **Select Model** pulldown. Click it and choose `qwen2.5-coder:7b`.

Do this every time you start the app. It does not always come up on the right model, and every other model on the machine is the wrong one for this class.

Type this line into Ollama's message box:

```
Write a Python program using pygame that implements the game in the PRD.md file.
```

Now attach `PRD.md`. There are two ways, and either is fine:

- **Use the plus sign.** Click the **+** button next to the message box, then find your way to `swdev`, then `game`, and pick `PRD.md`.
- **Drag it in.** In Terminal, type `open .` — that opens a Finder window on the folder you are standing in. Drag `PRD.md` from there onto the message box.

Press Return.

You attach the file instead of retyping it. A pasted PRD is a copy, and copies drift. Attaching means what Ollama reads and what you check against later are the same document, word for word.

## Step 4: Put the code in a file

Wait for Ollama to finish. This takes a while, and a half-written block can look finished.

Ollama may show more than one code block. Skip any block labeled **bash**.

Find the block labeled **python**. Click the **Copy** button in its upper right corner.

Then:

```
touch game.py
cot game.py
```

Paste the code into the CotEditor window and save with **Command-S**.

You now have two files open in the editor, `PRD.md` and `game.py`, in two tabs. That is how it stays for the rest of the unit.

## Step 5: Run it

```
uv add --script game.py pygame
uv run game.py
```

## Step 6: Keep fixing it until it runs

**Expect a crash the first time.** Red text in Terminal instead of a window means the program never ran.

That is normal. It does not mean you did anything wrong.

Fix it like this:

1. Copy the last several lines of the red text.
2. Go back to Ollama, in the same chat.
3. Paste it and add: "This crashed with the error above. Please fix it."
4. Copy the new **python** block.
5. Click into the `game.py` tab. Select everything with **Command-A**, paste over it with **Command-V**, save with **Command-S**.
6. Run it again.

Repeat until a window opens. It may take several rounds.

One thing about replacing the whole file: the note at the top that tells uv you need pygame gets wiped along with the old code. If the program says it cannot find pygame, run `uv add --script game.py pygame` again. That is all it means.

## Step 7: Play it and write down what is wrong

You have a game. Now find out what kind.

Play it for a few minutes. Do not look at the code. Watch the screen and write down anything you want changed.

Here is what to look for. These are the things Ollama decides for you when your PRD says nothing:

- **Can you win?** Does the score climb forever, or does the game end?
- **Can you lose?** What happens when you fail?
- **Is it too easy, or impossible?** If something plays against you, how fast is it? An opponent that never misses is not a game.
- **How big is the window?** How fast does everything move?
- **What color is everything?**
- **Do the right keys do the right things?**

Write each one on paper as you find it. You are making a list.

## Step 8: Put your list in the PRD

Click into the `PRD.md` tab. Under your one line, add a section for each thing on your list.

A section is a heading and a line or two under it:

```
## The window
600 pixels wide, 400 pixels tall. Blue background.

## Winning and losing
First to 11 points wins. The game stops and shows who won.

## The other paddle
The computer moves it. It moves 2 pixels per frame, so it can be beaten.
```

Two rules for what you write.

**Use numbers.** "The ball moves 4 pixels per frame" is something you can check by watching. "The ball moves fast" is not.

**Say what should happen, not how to make it happen.** The how is Ollama's job.

Save with **Command-S**.

## Step 9: Ask again, with the fuller PRD

Start a **new chat** in Ollama.

Check the **Select Model** pulldown still says `qwen2.5-coder:7b`.

Attach both files this time — `PRD.md` and `game.py` — and type:

```
The PRD describes what this program should do. The Python file is what I
have so far. Change the program so it matches the PRD.
```

Press Return, then take the new code back into `game.py` the same way you did in Step 6.

Both files, every time. `game.py` is what your program *does* right now. `PRD.md` is what it is *supposed* to do. A chat that gets only the code cannot tell which parts are what you wanted.

## Step 10: Play it again and check every line

Put your PRD next to the window. Go down it line by line.

For every sentence you wrote, look at the screen and decide whether it is true.

If something does not match, tell Ollama in one sentence what is wrong: "The game does not stop at 11 points. It keeps going."

If your PRD does not say something clearly enough for you to check it, that is a problem with your PRD. Fix the PRD too.

Repeat Steps 7 through 10 until the game matches your PRD.

## Step 11: If the chat gets slow

By now you may have gone back and forth several times, and noticed it getting slower. The first answer came back quickly. The sixth one crawls.

That is not your computer wearing out.

An AI has no memory between messages. To answer your sixth question it re-reads the whole conversation — your PRD, all the code, every error you pasted — and then works out what to say. The longer the chat, the more it re-reads, and the longer you wait.

The fix is to start a new chat:

1. Start a **new chat** in the Ollama app.
2. Attach `PRD.md`.
3. Attach `game.py`. Save it in CotEditor first with **Command-S**, so what you attach is the version that actually runs.
4. Say what you still need changed.

You lose nothing. Everything that matters is in those two files. That is exactly why the PRD is a document and not a conversation.

There is no rule for when to do this. No "every five messages." Do it when the waiting starts to annoy you. Noticing that for yourself is the skill.

## Step 12: Save your work

```
cd ..
git add .
git commit -m "Project 04: base game"
git tag p04
```

A **tag** is a bookmark on a commit. `git tag p04` labels the snapshot you just took, so you can find it by name later.

If a later project breaks your game and you want this version back:

```
git checkout p04 -- game/game.py
```

That restores the Project 04 `game.py` and leaves everything else alone.

To see every bookmark you have made:

```
git tag
```

## Step 13: Show it to Mr. Salemi

Play your game in front of him, with your PRD open beside it.

He will ask what your PRD says and whether the game does it. That is the whole check.
