In Project 03 you handed Ollama a prompt somebody else wrote. From here on, the prompts are yours. This project starts the game you will build for the rest of the term, and it starts with one piece of it: a player you can move with the keyboard.

# Your game, one piece at a time

Your teacher has assigned you one of five classic games: Pong, Breakout, Snake, Space Invaders, or Frogger. You will build it across the rest of this unit, one project at a time. You will never ask for the whole game at once.

Here is why. When you ask an AI for one small thing and what comes back is wrong, you know what caused it: the one thing you just asked for. When you ask for a whole game and it comes back wrong, you have no idea which part of your request the AI misread. Since you do not read the code, working in small pieces is the only way you can tell.

This project is the first piece. A window, and a player in it that moves when you press a key. No ball, no score, no enemies. Just movement.

# The PRD

A **PRD** is a Product Requirements Document. It is a written description of what your program should do, in plain English, with no code in it.

Your PRD is the record of your game. Your chat with Ollama is not. Chats get long and slow, and you will throw several of them away before this unit is over. The PRD stays, it grows a little every project, and it is what you check your finished game against.

Your PRD is also your prompt. When it is written well, you paste it straight into Ollama.

# Exercise 1: Get Your Player Moving

## Step 1: Make your game folder

```
cd $HOME
cd swdev
mkdir game
cd game
```

Projects 01 through 03 each got their own folder, because each one was a throwaway. This folder is different. It holds your game for the rest of the term, and every project from here on happens inside it.

## Step 2: Write your PRD

```
pico PRD.md
```

Type this in, filling in the parts in angle brackets. Delete the angle brackets when you do.

```
# PRD: <the name of your game>

## The window
<How big it is, in pixels. What color the background is.>

## The player
<What shape it is, how big it is in pixels, and what color.>
<Where on the screen it starts.>

## The controls
<Which keys the player uses.>
<What each key does.>
<Does the player keep moving while the key is held down, or move
once per press?>

## The edges
<What happens when the player reaches the edge of the window.>
```

Save and exit: **Control-O**, **Return**, **Control-X**.

Find your game in the section below and use it to fill in the blanks. Read only your own game.

### If your game is Pong

The player is a paddle: a tall, narrow rectangle about 10 pixels wide and 80 pixels tall, sitting near the left edge, halfway down. The Up arrow moves it up and the Down arrow moves it down. It keeps moving while the key is held down. It stops at the top and bottom of the window instead of sliding off.

### If your game is Breakout

The player is a paddle: a wide, flat rectangle about 80 pixels wide and 10 pixels tall, near the bottom of the window, centered. The Left arrow moves it left and the Right arrow moves it right. It keeps moving while the key is held down. It stops at the left and right edges instead of sliding off.

### If your game is Snake

The player is a small square, about 20 pixels on each side, starting in the middle. This one is different from the others: **it never stops moving.** The arrow keys change which direction it is traveling. They do not start it or stop it.

It should also move in steps, not smoothly — one square-length at a time, about ten times a second. A snake is not a sliding block. When it reaches an edge, have it come back on the opposite side of the window.

### If your game is Space Invaders

The player is a ship: a rectangle about 40 pixels wide and 20 pixels tall, at the bottom of the window, centered. The Left arrow moves it left and the Right arrow moves it right. It keeps moving while the key is held down. It stops at the left and right edges instead of sliding off.

Your ship does not shoot yet. That is the next project.

### If your game is Frogger

The player is a frog: a small square about 20 pixels on each side, at the bottom of the window, centered. All four arrow keys move it: up, down, left, and right.

This one is different from the others: **the frog hops.** One key press moves it about 40 pixels, once. Holding the key down does not make it keep going. Say that clearly in your PRD, because an AI will assume the usual thing if you do not. It stops at the edges of the window.

## Step 3: Turn your PRD into a prompt

Open the **Ollama** app. Check that the model at the bottom of the window says `qwen2.5-coder:7b`.

You are not going to retype your PRD into the chat. You are going to attach the file itself, so that what Ollama reads and what you check against later are the same document, word for word.

Type this line into Ollama's message box:

```
Write a Python program using pygame that does the following.
```

Now attach `PRD.md`. There are two ways, and either is fine:

- **Use the paperclip.** Click the paperclip button next to the message box, then find your way to `swdev`, then `game`, and pick `PRD.md`.
- **Drag it in.** In Terminal, type `open .` — that opens a Finder window on the folder you are standing in. Drag `PRD.md` from there onto the message box.

Press Return.

Attaching beats pasting for a reason worth knowing: a pasted PRD is a copy, and copies drift. From here to the end of the unit, `PRD.md` is the one description of your game, and every time you change it, the next thing you attach is already up to date.

## Step 4: Copy the code

Ollama may show more than one code block. Skip any block labeled **bash**. Find the block labeled **python** and click the **Copy** button on that one.

## Step 5: Put the code in a file

```
pico game.py
```

Paste the code. Save and exit: **Control-O**, **Return**, **Control-X**.

## Step 6: Tell uv this program needs pygame

```
uv add --script game.py pygame
```

## Step 7: Run it

```
uv run game.py
```

## Step 8: If it crashes

If you get red text in Terminal instead of a window, the program never ran. Copy the last several lines of that error, go back to Ollama in the same chat, paste it, and add: "This crashed with the error above. Please fix it."

Replace `game.py` with the corrected code — `rm game.py`, then repeat Step 5 — and run it again. If it crashes again, do it again with the new error.

## Step 9: Check it against your PRD

Once it runs, do not look at the code. Put your PRD next to the window and go down it line by line. For every sentence you wrote, look at the screen and decide whether it is true.

- Is the window the size and color you asked for?
- Is the player the shape, size, and color you asked for?
- Does it start where you said it should?
- Does each key do what you said it does?
- Does it move the way you said — while held, or once per press?
- Does the right thing happen at the edges?

Every one of those has to be true. If your PRD does not say something clearly enough for you to check it, that is a problem with your PRD, not with the AI.

## Step 10: If it runs but does not match

Go back to Ollama and tell it, in a sentence, what is wrong: "The paddle slides off the top of the window. It should stop at the top edge." Then fix the same thing in `PRD.md` if the reason it went wrong is that your PRD was vague.

## Step 11: If the chat gets slow

By now you may have gone back and forth with Ollama several times, and you may have noticed it getting slower. The first answer came back quickly. The sixth one crawls.

That is not your computer wearing out and it is not a mistake you made. An AI has no memory between messages. To answer your sixth question it re-reads the entire conversation — your PRD, all the code it wrote, every error you pasted — and then works out what to say. The longer the chat, the more it has to re-read, and the longer you wait.

The fix is to stop feeding the long one and start a new chat:

1. Start a **new chat** in the Ollama app.
2. Attach `PRD.md`, the same way you did in Step 3.
3. If you already have code that runs, attach `game.py` too, and say what you still need changed.

Both files, every time. `game.py` is what your program *does* right now. `PRD.md` is what it is *supposed* to do. A fresh chat that gets only the code has no way to tell which parts of it are what you wanted and which parts are the problem you are trying to fix.

You lose nothing by starting over. Everything that matters about your game is in those two files, which is exactly why the PRD is a document and not a conversation.

There is no rule for when to do this — no "every five messages." Do it when the waiting starts to annoy you. Noticing that for yourself is the skill; you will use it in every project from here on.

## Step 12: Save your work

```
cd ..
git add .
git commit -m "Project 04: player moves"
git tag p04
```

A **tag** is a bookmark on a commit. `git tag p04` puts a label on the snapshot you just took, so you can find it later by name instead of hunting through a list. Every project from here on ends with a commit and a tag.

Here is what that buys you. If a later project breaks your game and you want the version that worked, you can bring back an old file:

```
git checkout p04 -- game/game.py
```

That puts the Project 04 version of `game.py` back and leaves everything else alone. To see every bookmark you have made:

```
git tag
```
