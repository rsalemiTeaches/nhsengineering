In Project 03 you handed Ollama a prompt somebody else wrote. From here on the prompts are yours.

This project starts the game you will build for the rest of the term. It starts with one piece of it: a player you can move with the keyboard.

# Your game, one piece at a time

Your teacher has assigned you one of five classic games: Pong, Breakout, Snake, Space Invaders, or Frogger.

You will build it across the rest of this unit, one project at a time. You will never ask for the whole game at once.

Here is why.

Ask an AI for one small thing and get something wrong back, and you know what caused it. It was the one thing you just asked for.

Ask for a whole game and get something wrong back, and you have no idea which part of your request it misread. You do not read the code, so small pieces are the only way you can tell.

This project is the first piece. A window, and a player in it that moves when you press a key.

No ball. No score. No enemies. Just movement.

# The PRD

A **PRD** is a Product Requirements Document. It describes what your program should do, in plain English, with no code in it.

Your PRD is the record of your game. Your chat with Ollama is not.

Chats get long and slow, and you will throw several of them away before this unit is over. The PRD stays. It grows a little every project.

It is also what you check your finished game against.

And it is your prompt. Written well, you hand it straight to Ollama.

# Exercise 1: Get Your Player Moving

## Step 1: Make your game folder

```
cd $HOME
cd swdev
mkdir game
cd game
```

Projects 01 through 03 each got their own folder, because each one was a throwaway.

This folder is different. It holds your game for the rest of the term. Every project from here on happens inside it.

## Step 2: Write your PRD

```
touch PRD.md
cot PRD.md
```

Type this into the CotEditor window. Fill in the parts in angle brackets, and delete the brackets when you do.

```
# PRD: <the name of your game>

## The window
<How big it is, in pixels. What color the background is.>

## The player
<What shape it is, how big it is in pixels, and what color.>
<Where on the screen it starts.>

## The controls
<Which keys the player uses.>
<What each key does.>
<Does the player keep moving while the key is held down, or move
once per press?>

## The edges
<What happens when the player reaches the edge of the window.>
```

Save with **Command-S**.

Leave the window open. You will add to this file in every project from here on.

Now find your game below and use it to fill in the blanks. Read only your own game.

### If your game is Pong

The player is a paddle. It is a tall, narrow rectangle, about 10 pixels wide and 80 pixels tall.

It sits near the left edge, halfway down.

The Up arrow moves it up. The Down arrow moves it down. It keeps moving while the key is held down.

It stops at the top and bottom of the window instead of sliding off.

### If your game is Breakout

The player is a paddle. It is a wide, flat rectangle, about 80 pixels wide and 10 pixels tall.

It sits near the bottom of the window, centered.

The Left arrow moves it left. The Right arrow moves it right. It keeps moving while the key is held down.

It stops at the left and right edges instead of sliding off.

### If your game is Snake

The player is a small square, about 20 pixels on each side. It starts in the middle.

This one is different from the others. **It never stops moving.**

The arrow keys change which direction it is traveling. They do not start it or stop it.

It should also move in steps, not smoothly. One square-length at a time, about ten times a second. A snake is not a sliding block.

When it reaches an edge, have it come back on the opposite side of the window.

### If your game is Space Invaders

The player is a ship. It is a rectangle about 40 pixels wide and 20 pixels tall.

It sits at the bottom of the window, centered.

The Left arrow moves it left. The Right arrow moves it right. It keeps moving while the key is held down.

It stops at the left and right edges instead of sliding off.

Your ship does not shoot yet. That is the next project.

### If your game is Frogger

The player is a frog. It is a small square about 20 pixels on each side, at the bottom of the window, centered.

All four arrow keys move it: up, down, left and right.

This one is different from the others. **The frog hops.**

One key press moves it about 40 pixels, once. Holding the key down does not make it keep going.

Say that clearly in your PRD. An AI will assume the usual thing if you do not.

It stops at the edges of the window.

## Step 3: Turn your PRD into a prompt

Open the **Ollama** app.

At the bottom of the window is the **Select Model** pulldown. Click it and choose `qwen2.5-coder:7b`.

Do this every time you start the app. It does not always come up on the right model, and every other model on the machine is the wrong one for this class.

You are not going to retype your PRD into the chat. You are going to attach the file itself.

That way what Ollama reads and what you check against later are the same document, word for word.

Type this line into Ollama's message box:

```
Write a Python program using pygame that implements the game in the PRD.md file.
```

Now attach `PRD.md`. There are two ways, and either is fine:

- **Use the plus sign.** Click the **+** button next to the message box, then find your way to `swdev`, then `game`, and pick `PRD.md`.
- **Drag it in.** In Terminal, type `open .` — that opens a Finder window on the folder you are standing in. Drag `PRD.md` from there onto the message box.

Press Return.

Attaching beats pasting, for a reason worth knowing. A pasted PRD is a copy, and copies drift.

From here to the end of the unit, `PRD.md` is the one description of your game. Every time you change it, the next thing you attach is already up to date.

## Step 4: Copy the code

Wait for Ollama to finish. Sometimes this takes a while, and a half-written block can look finished.

Ollama may show more than one code block. Skip any block labeled **bash**.

Find the block labeled **python**. Click the **Copy** button in its upper right corner.

## Step 5: Put the code in a file

```
touch game.py
cot game.py
```

Paste the code into the CotEditor window and save with **Command-S**.

You now have two files open in the editor, `PRD.md` and `game.py`, in two tabs. That is how it stays for the rest of the unit.

## Step 6: Tell uv this program needs pygame

```
uv add --script game.py pygame
```

## Step 7: Run it

```
uv run game.py
```

## Step 8: If it crashes

Red text in Terminal instead of a window means the program never ran.

Copy the last several lines of that error. Go back to Ollama in the same chat, paste it, and add: "This crashed with the error above. Please fix it."

Ollama sends back corrected code. Copy the **python** block.

Click into the `game.py` tab in CotEditor. Select everything with **Command-A**, paste over it with **Command-V**, and save with **Command-S**.

Then run it again. If it crashes again, do the same thing with the new error.

One thing to know about replacing the whole file. Step 6 wrote a short note at the top of `game.py` telling uv this program needs pygame. Selecting everything wipes that note out along with the old code.

If the program then says it cannot find pygame, run Step 6 again. That is all it means.

## Step 9: Check it against your PRD

Once it runs, do not look at the code.

Put your PRD next to the window and go down it line by line. For every sentence you wrote, look at the screen and decide whether it is true.

- Is the window the size and color you asked for?
- Is the player the shape, size and color you asked for?
- Does it start where you said it should?
- Does each key do what you said it does?
- Does it move the way you said — while held, or once per press?
- Does the right thing happen at the edges?

Every one of those has to be true.

If your PRD does not say something clearly enough for you to check it, that is a problem with your PRD, not with the AI.

## Step 10: If it runs but does not match

Go back to Ollama and tell it in one sentence what is wrong. For example: "The paddle slides off the top of the window. It should stop at the top edge."

Then fix the same thing in `PRD.md`, if the reason it went wrong is that your PRD was vague.

## Step 11: If the chat gets slow

By now you may have gone back and forth with Ollama several times. You may have noticed it getting slower. The first answer came back quickly. The sixth one crawls.

That is not your computer wearing out, and it is not a mistake you made.

An AI has no memory between messages. To answer your sixth question it re-reads the whole conversation — your PRD, all the code it wrote, every error you pasted — and then works out what to say.

The longer the chat, the more it has to re-read, and the longer you wait.

The fix is to stop feeding the long one and start a new chat:

1. Start a **new chat** in the Ollama app.
2. Attach `PRD.md`, the same way you did in Step 3.
3. Attach `game.py`. Save it in CotEditor first with **Command-S**, so what you attach is the version that actually runs.
4. Say what you still need changed.

Both files, every time.

`game.py` is what your program *does* right now. `PRD.md` is what it is *supposed* to do.

A fresh chat that gets only the code has no way to tell which parts of it are what you wanted, and which parts are the problem you are trying to fix.

You lose nothing by starting over. Everything that matters about your game is in those two files. That is exactly why the PRD is a document and not a conversation.

There is no rule for when to do this. No "every five messages." Do it when the waiting starts to annoy you.

Noticing that for yourself is the skill. You will use it in every project from here on.

## Step 12: Save your work

```
cd ..
git add .
git commit -m "Project 04: player moves"
git tag p04
```

A **tag** is a bookmark on a commit. `git tag p04` puts a label on the snapshot you just took, so you can find it later by name instead of hunting through a list.

Every project from here on ends with a commit and a tag.

Here is what that buys you. If a later project breaks your game and you want the version that worked, you can bring back an old file:

```
git checkout p04 -- game/game.py
```

That puts the Project 04 version of `game.py` back and leaves everything else alone.

To see every bookmark you have made:

```
git tag
```
