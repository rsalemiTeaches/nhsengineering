You have a working game. So does everybody else with your assignment, and right now they all look the same.

This project makes yours different. Six things have to change: the name, the theme, the colors, your sprite, the other sprites, and one rule.

Those six are on your checkoff sheet as six separate lines. All six get checked before this project is done.

At the end you show it to Mr. Salemi, and he should not be able to mistake it for the plain version.

# Virus Hunter, not Asteroids

Nobody in this class was assigned Asteroids, so here is what one of these looks like using that game.

Base Asteroids is a white triangle ship in the middle of a black screen. It shoots white dots at gray rocks. A rock you hit breaks into two smaller rocks.

**Virus Hunter** is the same program underneath. Every one of the six changed:

- **Name** — Virus Hunter.
- **Theme** — you are fighting an infection.
- **Colors** — the background is pale blue like a microscope slide. Viruses are green. Antibodies are bright yellow.
- **Your sprite** — the ship is now a hypodermic needle, pointing where it shoots.
- **The other sprites** — the rocks are viruses, round and lumpy with spikes. The bullets are antibodies.
- **A new rule** — a big virus breaks into two medium ones, and each medium one breaks into two small ones. The small ones move fastest and are worth the most points.

Nothing about that is a new game. It is Asteroids with every visible thing decided on purpose.

Notice how the theme does the work. Once it is an infection, the needle, the green, and the splitting viruses all follow. Six unrelated changes are a mess. Six changes that agree with each other are a design.

Every one of them was made one at a time, with the PRD updated first.

# One change at a time

Each of the six is its own small loop:

1. Write the change into `PRD.md`.
2. Ask Ollama for that one change.
3. Put the new code in `game.py` and run it.
4. Check the change worked, and check nothing else broke.

Never ask for two changes at once. When something comes back wrong, you want to know which request caused it — and you do not read the code, so the only way to know is to have asked for one thing.

# Exercise 1: Make It Yours

## Step 1: Decide what your version is

Six things have to change. Each one is a separate line on your checkoff sheet, and each one gets checked off on its own.

Decide all six now, on paper, before you change anything.

**1. A new name.** Virus Hunter, Brick Buster, Space Cows. Whatever it is, it is not the name of the game you were assigned.

**2. A theme.** What is your game about now? Virus Hunter is about fighting an infection. Space Cows is about cows in space. The theme is what makes the other five choices agree with each other.

**3. A color scheme.** Pick your colors on purpose. Background, sprites, text. Write down what each one is.

**4. A new look for your sprite.** The thing you control. Change its shape, its size, its color, or where it sits.

**5. A new look for the other sprites.** The ball, the food, the cars, the invaders — whatever else is on your screen.

**6. A rule the base game did not have.** This is the one that makes it play differently. Some ideas:

- A powerup that appears and changes something for a while.
- Something that speeds up as the game goes on.
- A second thing to dodge, catch, or hit.
- A limited number of tries.
- One part of your sprite that behaves differently from the rest, the way a paddle's edge can angle a ball.

Your rule does not have to be on that list. It has to be something you can watch happen on the screen.

Write all six down before you start. You will work through them one at a time.

## Step 2: Rename the game in your PRD

```
cd $HOME
cd swdev
cd game
cot PRD.md
```

Your PRD starts with a line naming your assigned game. Change it to your name, and keep the game it came from:

```
This is Virus Hunter. It is based on Asteroids.
```

Keep the "based on" part. Ollama still needs to know what game it started from.

Save with **Command-S**.

## Step 3: Make your first change

Pick one thing off your list. Just one.

Write it into `PRD.md`, in the section it belongs to. If there is no section for it, add one.

Here is what the Virus Hunter background change looked like:

```
## The window
600 pixels wide, 400 pixels tall. Pale blue background, like looking
through a microscope.
```

Save with **Command-S**.

Use numbers wherever you can, the same as last project. "Viruses are 30 pixels across" is checkable. "Viruses are big" is not.

## Step 4: Ask Ollama for that one change

Start a **new chat**. Check the **Select Model** pulldown still says `qwen2.5-coder:7b`.

Attach `PRD.md` and `game.py`. Use the **+** button, or drag them in.

Then type:

```
The PRD describes what this program should do. The Python file is what
I have working so far. Make this one change:
```

Write your change next, in the same words you just put in the PRD. Finish with:

```
Do not change anything else about the program.
```

That last line matters. Without it, an AI will often rewrite parts you never asked it to touch.

Press Return.

## Step 5: Put the new code in and run it

Copy the **python** block.

Click into the `game.py` tab. Select everything with **Command-A**, paste over it with **Command-V**, save with **Command-S**.

```
uv run game.py
```

If it says pygame is not found, run `uv add --script game.py pygame` and try again. Replacing the whole file wiped the note at the top that told uv what this program needs.

If it crashes, use the same loop as Project 04: copy the error, paste it into the same chat, add "This crashed with the error above. Please fix it."

## Step 6: Check the new thing, then check the old things

Two checks, not one.

**Did the change happen?** Look at the screen. Is it what your PRD now says?

**Does everything else still work?** Play a full round. Move your sprite. Score a point. Get to the end of the game.

An AI rewriting your program can break something that used to work. A paddle that used to stop at the edge now slides off. A game that used to end at 11 now runs forever.

Nobody tells you when this happens. Checking is your job, and your PRD is the checklist.

If something broke, say so plainly: "The game used to stop at 11 points and now it keeps going. Please fix that and leave everything else alone."

## Step 7: Commit, then do the next one

```
cd ..
git add .
git commit -m "Pale blue background"
cd game
```

Commit after every change that works. Write what you changed in the message.

That way a bad change later costs you one step, not your whole game. To get back the last version that worked:

```
git checkout HEAD~1 -- game/game.py
```

Now go back to Step 3 and do the next thing on your list.

Keep going until all six are done. Check them off your sheet as they work.

## Step 8: If the chat gets slow

Same as Project 04. Start a new chat, attach `PRD.md` and `game.py`, say what you still need.

Save `game.py` in CotEditor before you attach it, so what you send is the version that actually runs.

## Step 9: Tag your finished version

```
cd ..
git add .
git commit -m "Project 05: my own version"
git tag p05
```

## Step 10: Show it to Mr. Salemi

Play your version in front of him with your PRD open and your checkoff sheet beside it.

He goes down the six lines with you. For each one you show him the change on screen and the line in your PRD that describes it.

All six, or the project comes back.
